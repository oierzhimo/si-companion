# 首轮开发任务

首个可交付结果是在 Windows 桌宠的“自由聊聊”中发送文字、图片、文件和语音，让小祀理解内容并返回真实可查看或播放的消息。QQ 可用于重跑媒体基线，首轮通过条件落在桌宠实际界面。

## 1. 做通用消息和回复的最小实现

从 `si-desktop-pet/src/si_pet/conversation_ui.py` 和 `conversation.py` 追踪一次正常发送。对照 QQ 的 `media_support.py`、`image_prepare.py`、`model_router.py`、`service_reply.py` 和本地媒体调用，选择能保持现有行为的最小复用边界。先为 Windows 桌宠建立一条明确的调用链。

1. 客户端构造用户消息，带有稳定 ID、会话 ID、文字及附件描述。附件要有类型、大小与可验证的内容身份。设计时保留纯文本旧会话的读取路径。
2. 能力层接收消息，识别当前内容类型，调用相应的提取、识图、ASR、文本回复、TTS 或绘图。先用固定测试替身跑通失败和成功分支，再逐项替换成实际服务。
3. 能力层返回回复和真实媒体数据或引用，同时给出生成、交付和失败状态。桌宠用自身组件展示。QQ 若复用同一层，在适配器边界转换为 OneBot `text`、`image`、`record` 等段。
4. 异步执行耗时任务，支持模型等待、取消和失败恢复，保留原消息和附件关联。重试使用同一个请求身份，避免重复生成或重复发送。

文本回复继续沿用小祀身份与管理员关系。明确的语音或绘图请求走对应能力。ASR 暂未接入正式链路，第一轮可单独验证语音文件采集、转写和转写失败，确认后再联入正常对话。模型或服务准备失败应在交互界面显示可读状态。

## 2. 在 Windows 真实界面验收

| 操作 | 核对点 |
|---|---|
| 发一条普通文字，继续追问 | 用户消息、角色回复及上下文完整，老文本会话可读 |
| 发图片并询问具体内容 | 正确识别所引用图片，能打开相应附件 |
| 发有已知正文的文本或文档 | 提取结果与内容一致，错误文件有清晰提示 |
| 发一段短语音 | 确认附件可读、可转写，回复使用正确语义 |
| 明确请求小祀说一句话 | 结果是可播放音频，客户端显示与播放状态可核对 |
| 要求生成带数量、位置与背景约束的图片 | 保留原描述与生成图，检查完成后的真实图像、核对结论和界面可见状态 |
| 断开服务、超时、重试或重开窗口 | 状态可恢复，历史完整，重复内容不会再次入账 |

保留源码测试与实际 UI 测试两类证据。Windows a10 可并行收尾，原生全屏与拖拽应在真实前台环境验证。完整绘图题见 [项目介绍](PROJECT.md)，简单样例用于排查流程。

## 3. 第二阶段验证跨端消息

首选单台 Windows 和 Android。用现有配对与 TLS 验收结果作起点，扩展会话和附件的交换规则。先定清协议兼容策略、消息幂等、附件可达性与恢复状态，再增加第二台 PC 和 HarmonyOS。

首个跨端验收用例是从 Android 发送图片或语音，在 Windows 查看同一条消息、打开附件、收到小祀回复并继续对话。逐项检查反向发送、离线后恢复、重启、重复交换和接收失败。存档迁移、安装与签名在隔离环境中先复验。
